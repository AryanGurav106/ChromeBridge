# Literature & landscape survey — page observation / DOM representation

Surveyed 2026-11-16. Scope: work on turning a live DOM into an agent-readable
observation, published roughly 2026 (weighted to H2). Everything in the
project's existing "already knows" set is excluded unless a *specific fact
inside* a known source turned out to be load-bearing and unrecorded.

**Verification policy used here.** Every claim below was read off the arXiv
abstract or HTML page for that identifier, not off a search-result summary. Two
figures that search summaries attributed to papers were checked and found absent
from the source; they are named in §4 so nobody re-imports them. Where a number
came through a page-summarising fetch rather than my own reading of a table, it
is marked **(summarised)** — the identifier and direction are reliable, the last
digit may not be.

## 1. Findings that could change this project's design

### 1.1 The compaction bet may invert for frontier models — and the measurement is directly against us

**Read More, Think More: Revisiting Observation Reduction for Web Agents.**
Enomoto, Obara, Zhang, Oyamada. arXiv:2604.01535v1, 2 Apr 2026. Preprint, no
peer-reviewed venue listed.

*What it measured:* task success on WorkArena L1 (330 tasks = 33 task types ×
10 seeds), holding everything fixed except the observation format — BrowserGym
accessibility tree vs. raw HTML — across 11 models and several thinking budgets.

Results table (summarised), success %:

| model (thinking) | a11y | HTML | Δ |
|---|---|---|---|
| gpt-5.1 (high) | 55.8 | 73.3 | **+17.5** |
| Claude Sonnet 4.6 | 52.4 | 67.0 | **+14.6** |
| gpt-5.1 (low) | 49.1 | 57.9 | +8.8 |
| gemini-2.5-flash (budget 16384) | 45.5 | 56.7 | +11.2 |
| gemini-2.5-flash (budget 128) | 28.5 | 34.5 | +6.0 |
| o3-mini (high) | 39.7 | 32.1 | −7.6 |
| gpt-oss-120b (high) | 46.7 | 38.8 | −7.9 |
| gpt-oss-20b (high) | 46.4 | 27.6 | **−18.8** |
| Qwen3-VL-235B-Thinking | 45.0 | 39.8 | −5.2 |
| Llama-3.1-70B | 18.2 | 3.6 | −14.6 |

The HTML advantage *grows with thinking budget* for both models where budget was
swept. The authors' explanation is that stronger models exploit layout
information present in HTML for action grounding, while weaker models hallucinate
element references on longer inputs.

**Why this matters here, stated at full strength.** This project's entire
representation programme optimises retention-per-token, and its own head-to-head
(#17) settled the architecture question by showing the AX tree costs 7.15× the
tokens for 4pp more recall. This paper measures a *different axis* on the same
pair and finds the opposite sign for exactly the regime ChromeBridge runs in: a
frontier model at high reasoning effort. Recall is not success, and #75 already
records that this project has never measured success.

**What would change.** Nothing immediately — the paper does **not** measure
ChromeBridge. Its `a11y` arm is BrowserGym's AXTree, which this project has
already measured as information-poor per token; ChromeBridge is a third point
that is denser than AXTree, not a smaller one. The honest reading is that the
paper puts a *hypothesis* on the table that this project cannot currently
refute: that what compaction removes (layout cues, sibling context, raw
attributes) is load-bearing for a strong model's grounding, and that the cost
shows up in success rather than in recall.

**What it would cost to answer.** One arm added to an existing harness:
ChromeBridge listing vs. raw/`cleaned_html` on the same tasks with the same
model, scored on success. §1.2 supplies the substrate.

**Caveats, which are large and are the authors' own.** Single benchmark
(WorkArena L1 / ServiceNow — one application family, which the authors say makes
generalisation unverified); "capability" is proxied by proprietary-vs-open-source
and is therefore confounded; only id-based grounding was tested. There are
sign exceptions inside the table (Qwen3-VL-30B gains +2.8 with HTML).

**One live tension worth recording.** WorkArena's own paper (arXiv:2403.07718,
already known here) found coordinates on an AXTree *hurt* on complex pages, and
#26 cited that when making `box()` opt-in. This paper says layout information in
HTML *helps* strong models. These are not the same quantity — explicit numeric
coordinates vs. structural/attribute cues carried by markup — but they point
opposite ways on the same benchmark family and should not be quoted as agreeing.

### 1.2 The success-based ruler #75 concluded did not exist, does exist — on component libraries

**ComponentBench: Diagnosing Component-Level Failures in Computer-Use Agents.**
Guan, Lin, Cheng-Yue, Wang, Zhou. arXiv:2608.18307v1, 18 Aug 2026. **Accepted at
COLM 2026.** Code: `github.com/TianchenGuan/ComponentBench`; data and runs on
HuggingFace (`TianchenGuan/ComponentBench`).

*What it measured:* 2,910 programmatically verified tasks over a library-agnostic
ontology of **97 canonical UI component types**, across widely used component
libraries, with seven models evaluated under **four observation/action spaces** in
one shared harness.

Construction, which is the part that matters:

- Pages are **generated interactive Next.js apps**, not live sites and not static
  snapshots — "real interactive Next.js pages rather than static mockups".
  Self-hosted, so deterministic and replayable.
- **Programmatic oracle, not an LLM judge**: "Every task is paired with a
  programmatic verifier that checks the committed end state." A JS checker
  evaluates a success predicate against live component state and reveals a
  `#cb-success-banner`.
- **Step values are intact and hidden from the agent**: "Target values and success
  predicates reside in React component closures."
- **Cleaned human reference trajectories** are included, for success *and*
  interaction efficiency. Even the fastest agent configuration takes **3.7×** the
  matched human time.
- Observation/action spaces: AX-tree (+screenshot, act by element id),
  Set-of-Marks (+screenshot, act by id), Pixel (screenshot only, act by
  coordinates), and Browser-Use (richer tool surface with serialised DOM).
- Headline: changing **only** the observation/action space shifts success by
  **more than 30 points** for one model — GPT-5 mini falls from **83.1%**
  (accessibility-tree) to **48.9%** (coordinate-only Pixel).

**Why this matters here.** #75 tried to measure success retention, and the
attempt failed on the *substrate*: Mind2Web snapshots leak the answer through
anomalous `backend_node_id` ordering, carry no CSS so responsive duplicates are
indistinguishable, and have the step VALUE stripped. ComponentBench fixes all
three by construction — hidden target values, a deterministic oracle, real CSS —
and it is centred on exactly the component families this project was built
against (the fixture corpus is Radix/shadcn/HeadlessUI/MUI; the ontology is
library-agnostic across those).

It also makes a success-axis comparison against **browser-use** possible on
neutral ground, which #33's admission-rule A/B could not do (and which #78
retired as obsolete now that browser-use's AX path is default).

**What it would change.** It unblocks `docs/SUCCESS-RETENTION.md`'s rerun and
`OPEN.md` item 11's success half, on a substrate whose failure modes are not the
ones that defeated the last attempt.

**What it would cost.** The harness is BrowserGym-shaped and the four existing
arms are already implemented; adding ChromeBridge as a fifth observation space is
the work. Note the project's own constraint: ChromeBridge drives the *user's real
Chrome* through an extension, so running against a local Next.js app needs the
gate granted for `localhost` — `tools/run_flows.py`'s throwaway-profile pattern
already does exactly this.

**Caveats.** Not live-internet pages. **Per-step element ground truth is not
described** in the paper — what exists is final-state verification plus human
reference traces plus BrowserGym trace logs. So this does *not* replace
Mind2Web's element-recall ruler; it is the complementary success ruler.
I could not verify per-step labels are absent, only that the paper does not
describe them — treat as **UNVERIFIED**.

### 1.3 Region-level observation beats element-level — and its case against rule-based regions is argued, never measured

**Region4Web: Rethinking Observation Space Granularity for Web Agents.**
Kwon, Lee. arXiv:2605.07134v1, 8 May 2026.

*What it measured:* WebArena (812 tasks), reorganising the AXTree into functional
regions and giving the actor a compact region-level digest (**PageDigest**) that
persists across steps.

(summarised) WebArena success rate and observation tokens:

| actor | SR base | SR +PageDigest | tok base | tok +PageDigest |
|---|---|---|---|---|
| GPT-5.1 | 45.2 | 47.5 | 6,116 | 4,302 (−30%) |
| Gemini 3.1 Flash-Lite | 39.4 | 41.6 | 6,705 | 3,207 (−52%) |
| DeepSeek-V3.2 | 40.4 | 43.4 | 7,158 | 4,521 (−37%) |
| Qwen3.5-27B | 38.2 | 39.9 | 5,767 | 2,654 (−54%) |
| AgentOccam (GPT-4o) | 40.6 | 41.3 | 4,025 | 3,365 (−16%) |
| SteP (GPT-4o) | 39.5 | **38.7** | 7,136 | 3,693 (−50%) |

WebArena-Lite ablation (165 tasks, GPT-5.1): base 48.5% / 5,410 tok →
+Region4Web 50.3% / 5,922 → +PageDigest **53.9% / 3,814**.

**The mechanism is learned, and that is the point of including it.** An
`EdgeClassifier` — a small MLP, not an LLM at inference — scores each
parent→child edge in the AXTree and cuts it if the score ≥ τ = 0.55. Inputs are a
16-dim node feature vector: a learned role embedding plus depth, subtree size,
child count, accessible-name presence, and child-role diversity. One bottom-up
traversal. An LLM is used only to generate training labels.

**The directly relevant fact.** The paper justifies the learned model with:

> "Deriving them through rule-based decomposition is insufficient"

…because "what each region is for varies with the page even for structurally
repeated patterns." **I checked for the ablation behind that sentence and it does
not exist.** Table 2 compares backbone / Region4Web / an element-level LCoW
variant / full PageDigest; Table 4 sweeps τ for the learned model only. No
landmark-based, sectioning-element-based, or depth-cutoff baseline is run. The
claim is argued, not measured.

**What this means here.** ChromeBridge already ships the rule-based version of
this idea — #26's off-viewport region hints name landmarks *and their refs*, and
#80 made them carry `aria-label`/heading text rather than tag names. The
project's governing rule forbids the learned classifier. What Region4Web supplies
is (a) independent evidence that *region-level* granularity is the right unit,
worth +1.7 to +3.0 SR with 16–54% fewer tokens, and (b) a load-bearing claim
against the project's approach with **no experiment behind it**, i.e. a cheap
experiment nobody has run: landmark/sectioning decomposition vs. the
EdgeClassifier on the same WebArena tasks.

**What would change.** Possibly nothing in the collector — the persistent
*digest* (a region summary carried across steps, rather than re-derived per read)
is the transferable part, and it is adjacent to `delta` (#16b/#30) but not the
same thing: a digest persists *structure*, `delta` transmits *change*.

**Cost.** Reading the digest construction properly, then one measurement.
The paper's own numbers show the digest, not the segmentation, carries most of
the gain (50.3% → 53.9% comes from adding PageDigest on top of Region4Web).

### 1.4 WebMCP has a declarative HTML surface in flight, and an open question that would make `page_tools` silently blind

Checked against the spec repo, **not** blogs — several 2026 blog posts state the
declarative attributes as shipped or as part of the standard, and that is wrong.

`github.com/webmachinelearning/webmcp` (spec first published 2025-08-13; repo
active 2026) says plainly:

> "WebMCP is currently focused on the imperative `document.modelContext.registerTool()` API described above, which is what the specification defines."

> "…it is not part of the specification at this time."

The declarative design lives in `declarative-api-explainer.md` in that repo and
proposes:

- on `<form>`: **`toolname`**, **`tooldescription`**, and **`toolautosubmit`** (a
  boolean letting an agent submit the form without a user check)
- on form controls: **`toolparamdescription`** (the control's existing `name`
  supplies the property name)
- CSS pseudo-classes `:tool-form-active`, `:tool-submit-active`
- `SubmitEvent.agentInvoked` (read-only) and `respondWith()`
- `ModelContext` events `toolactivated` / `toolcancel`
- a `<script type="application/ld+json">` response convention (marked as under
  debate)

**The actionable open question, quoted from the explainer's own list:** *how
declarative tools appear in `getTools()` and `executeTool()`, and whether agents
can invoke them through that interface* — still open, alongside input-schema
synthesis rules marked TBD.

**Why this matters here.** `page_tools` reads
`document.modelContext.getTools()`. If the declarative form lands and declarative
tools do **not** surface through `getTools()`, ChromeBridge reports "this page
declares no tools" for a page that declares tools *in its markup* — a false
negative of exactly the class this project treats as the worst direction, and one
nothing in the current tool surface could detect.

Second, **`toolautosubmit` is a page-authored declaration that an agent may
submit without a user check.** That interacts with two settled decisions:
#24 deleted the submit wordlists and made the picker answer only from what the
document declares (`type="submit"` / implicit submit), and the permission gate is
default-deny per origin. A page saying "submit me without asking" is a new kind
of declaration, and whether it outranks either of those is a policy call, not a
parsing one.

**What would change.** Today: nothing, correctly — the imperative API is the only
specified surface and `page_tools` reads it. This is a **watch item** with a
concrete trigger: the day `toolname` appears in the spec proper, `page_tools`
needs a declarative pass, and the submit picker and the gate each need a stated
answer on `toolautosubmit`.

**Cost.** Zero now. A markup scan plus two policy decisions later.

**It also corrects a stale external claim**, which is worth recording given #77's
WebMCP retraction: the declarative attributes are **not** in the standard, and
anyone reading 2026 blog coverage will be told otherwise.

### 1.5 A controlled environment for the readiness question — the nearest substrate that exists

**Constructing Challenging Browser-Use Tasks by Controlled Environment
Interventions.** Yin, Guan (equal contribution), Wang, Cao, Lin, Cheng-Yue, Long,
Wong, Dhingra, Wang, Zhou (Duke / Amazon). arXiv:2609.35814v2, 20 Oct 2026.
(Overlapping authorship with ComponentBench — same group.)

*What it measured:* 519 intervention variants in 29 families across four layers —
Seed (planted content/decoys), Server (structural corruption), Network (runtime
API interception: transient 5xx/401, 409 conflicts, stale data, forged 200s), and
Client (DOM/interaction: misaligned labels, swallowed clicks, overlays) — scored
against the website's final backend state.

The relevant one is the **"patience" primitive**, whose representative
interventions are **tail latency** and **progressive delay**. Pass rate under
patience interventions (summarised), with change from clean:

| agent | pass | Δ clean |
|---|---|---|
| Gemini-3.1-Pro | 48.0% | **−24.0** |
| GPT-5.4-mini | 8.0% | **−20.0** |
| Opus-4.7 | 32.0% | −8.0 |
| Gemini-3-Flash | 48.0% | −4.0 |
| GPT-5.4 | 52.0% | −4.0 |
| Sonnet-4.6 | 28.0% | 0.0 |

Humans on Human-140 (n = 7 tasks): 71.4% both attempts.

**What this is and is not.** It measures whether agents *cope with* slow and
asynchronously arriving content. It does **not** measure whether showing the
model a readiness/settling signal helps — nobody has measured that (§3.2). But it
is the first controlled, reproducible environment where latency is an independent
variable and success is the dependent one, which is precisely the harness that
experiment needs. The project currently has the signal (#70/#76/#77) and no way
to price it.

**What it would cost.** The expensive half is already built by someone else. The
project's half is one arm with the banner suppressed. Note §4: the cells are
small.

**Caveats.** Pass rates in multiples of 4.0 imply n = 25 per cell; the human cell
is n = 7; the paper itself says per-primitive samples are uncertain, and notes
that for text-based agents patience is among the *smallest* mean-score drops —
so the −24 point row should not be quoted as the typical effect.

## 2. Findings that confirm existing choices

**2.1 An independent agent arrived at this project's interactivity predicate,
almost exactly.** *WebChallenger: A Reliable and Efficient Generalist Web Agent*,
Hwang, Zhang, Padwal. arXiv:2606.10423v1, 9 Jun 2026. Its "clickable predicate"
(Appendix A.1.3) is a visibility/accessibility gate — excluding nodes not
rendered, carrying `disabled`, or `aria-hidden="true"` — plus at least one
positive signal: an interactable **tag**, an **event-listener attribute**
(`onclick`/`onmousedown`/`onmouseup`/`onkeydown`/`onkeyup`), an **ARIA role**, or
computed **`cursor: pointer`**. No class names, no pixel sizes, no framework
names, no wordlists in the predicate. Reported: WebArena 56.3, VisualWebArena
48.7, Online-Mind2Web 51.0, WorkArena 70.9 (summarised).

Two differences are in this project's favour and are worth keeping explicit:
it reads **event-listener attributes** only, where ChromeBridge wraps
`addEventListener` at `document_start` (#18 measured registered-listener tagging
as 60% of its accuracy gap, and #71 extended it to handler *properties* across
six events); and it **excludes `disabled`**, where #27 deliberately keeps a
disabled control because existence and operability are different questions — the
demoqa City-field case, the project's most-reported false negative.

Separately, WebChallenger's page division **groups sibling nodes that share tag
and class** — which is the fold signature #27 landed on after four rewrites.
Independent convergence on the same key.

**2.2 Everyone else calls this predicate a heuristic.** *WebServ: A Full-Stack
and RL-Ready Web Environment for Training Web Agents at Scale*, Lu et al.,
arXiv:2510.16252v2 (v2 stamped 17 May 2026) — "heuristically determines whether
elements are interactive": native controls, anchors with `href`, explicit
`onclick`, ARIA roles, computed `cursor: pointer`, excluding disabled. The
project's position that this set is a *declaration* set rather than a heuristic
set is a framing nobody else has adopted, and no paper found contradicts it.

**2.3 Scoped/bounded subtree reads as a protocol primitive.** *MCP-Driven
Accessibility Tree Standardization for AI-Powered Screen Reader Agents*,
Ramineni et al., arXiv:2608.24898v1, 13 Jul 2026. Proposes an MCP accessibility
server with `a11y://tree/{session}?root={nodeId}&depth={n}` — a bounded subtree
request instead of whole-tree serialisation — plus resource-update *notifications*
so the agent need not poll. That is `read_page(ref_id=…)` and (loosely) the
readiness signal, independently proposed. **Position paper: no measurements at
all**, Table I is qualitative Low/Medium/High, and the authors state no
cross-platform implementation exists. Confirms the shape, supplies no evidence.

**2.4 A DOM/declaration channel is theme-invariant where pixels are not.**
*Affora: A Design System for Agent-Friendly Interfaces*, Jin Gao (single author).
arXiv:2609.19125v1, 16 Sep 2026, cs.HC preprint. Study 2 (summarised):
DOM-channel completion **99.5% across tested themes**, matching native
presentation; pixel completion **92% vs 94%** for native controls; a visual-cue
sweep ranged 98.7–99.8% with no monotonic gain. This independently corroborates
#79's colour-invariance result (12/12 theme pairs, 0 changed lines, same-arm
floor 0) on a different corpus and a different metric.

**2.5 Exposing enumerable choices and state is worth a lot.** Same paper, Study 1
(summarised): plain semantic HTML reached **91%** agent success on a mid-tier
model while **eight component libraries ranged 86.7% → 68.3%**; in a repair
sequence, fixing semantics took success **43% → 67%**, and *then* exposing
choices and state took it **67% → 90%**. That second step is what #31 added
(`options=` / `count=` inline, declared constraints) and what #39/#40 added
(queryable declared state, `(read-only)`). Its principles P1 "state is stated",
P2 "presence over disclosure" and check S8 "machine-readable targets match the
visible interface" restate, from the authoring side, three rules this project
derived from defects — #27's existence-vs-operability split, and #80's
"rows that mean different things, printed the same".

Two transfer results are worth noting as element classes this project has not
explicitly tested: a **hidden-radio pattern** (WebShop completion 8% → 68%) and
**targets behind non-predictive labels** (shadcn-admin 23% → 64%). MUI and
Atomic CRM showed near-null changes.

**2.6 The WebMCP imperative API is the only specified surface** — see §1.4. Blog
coverage saying otherwise is wrong.

## 3. Areas searched where nothing new exists — stated explicitly

### 3.1 Declaration-based or structural record-boundary detection: nothing in 2026

Searched for 2026 work on record boundaries, list segmentation and repeated-
structure detection that is declaration-based rather than heuristic. **Nothing
new.** The most recent relevant item is *NEXT-EVAL: Next Evaluation of
Traditional and LLM Web Data Record Extraction* (arXiv:2505.17125, 2025) — a
**benchmark**, not a method, which frames the task as finding repeated groups of
related elements that "may be contiguous siblings or non-contiguous and nested
under different parents." The method literature remains MDR/DEPTA/IEPAD-style
repeated-pattern mining and sequence alignment, which the project already knows
and already surpassed in #27 by replacing a weighted signature with **exact
equality of sibling subtree shape**.

Region4Web (§1.3) is the only 2026 paper found that re-opens the segmentation
question at all, and it answers it with a learned classifier while asserting —
without measuring — that rules cannot work.

**Conclusion: the project's "exact sibling subtree shape + tag path + class"
answer is not superseded by anything published in 2026.**

### 3.2 Whether a readiness/settling signal shown to the model improves task success: no published evidence, either way

Two independent searches. **The project's belief is correct.** No paper found
ablates a settling/readiness signal against task success. What exists nearby:

- arXiv:2610.39282 (already known here) measures *wait rules*, i.e. when the
  agent should act — not what the model is told.
- BreakingWeb (§1.5) measures whether agents *cope with* latency, not whether a
  signal helps.
- Vendor/practitioner material (a Merj blog tracking "agent acts on stale DOM"
  rising ~44% → ~58% between Nov 2025 and Mar 2026; Lighthouse's experimental
  Agentic Browsing category scoring layout stability as a **pass ratio**, not
  end-to-end success) is **not** controlled evidence and should not be cited as
  such. Flagged **UNVERIFIED**; I did not confirm either methodology.

### 3.3 A benchmark with the full conjunction (live pages + per-step element labels + intact step values + agent loop): does not exist

**The project's belief is correct.** Checked ten-plus candidates. Each 2026
benchmark drops at least one leg:

| benchmark | live pages | per-step element labels | intact step values | agent loop |
|---|---|---|---|---|
| ComponentBench (2608.18307, COLM 2026) | generated apps, self-hosted | **not described** | yes (hidden in closures) | yes, 4 obs/action spaces |
| CAP (2608.08392, COLM 2026) | 108 real websites | not stated | not stated | yes, agent-as-judge |
| BreakingWeb (2609.35814) | instrumented stack | no | yes | yes, backend-state scored |
| LiveWeb-IE (2603.13773, ICLR 2026) | yes | n/a — extraction, not action | n/a | no action loop |
| Mind2Web | no (snapshots) | **yes** | stripped | no |
| Mind2Web-Live / WebCanvas | yes | milestone key-nodes, not per-action | — | yes |

ComponentBench and CAP are the two worth tracking; ComponentBench is the one that
is immediately usable (§1.2) because it is deterministic, oracle-scored and
released. Nothing supplies per-step element labels on live pages — that
conjunction remains unmet, which means **the Mind2Web element-recall ruler still
has no successor** and `MEASUREMENT.md` §6 stands as written.

### 3.4 Set-of-mark alternatives that report a TEXT representation: nothing applicable

The 2026 SoM work found is visual-vs-visual. *MAG: A Web-Agent Benchmark and
Harness for Multimodal Action and Guide Generation* (arXiv:2607.10079) runs what
its authors say is the first controlled SoM-vs-raw-pixel-coordinate comparison
with prompts, observations and scoring held fixed; the result is model-dependent
(a trained 9B model improved only under SoM, 13.2% vs 9.2%) — **(summarised,
abstract-level only; I did not verify the table)**. Neither arm is a text
representation, so it does not bear on this project. No 2026 paper found proposes
a textual alternative to SoM that is not already in the project's known set.

### 3.5 A genuinely heuristic-free "is this a control?" method: does not exist

This was searched hardest, since it is the project's core constraint and its
stated appetite. **Nothing found.** Every 2026 system that states its rule states
the same rule (§2.1, §2.2) and most call it a heuristic. No paper found uses
registered-listener interception as a primary admission signal — WebServ
monkey-patches `addEventListener` but only to annotate **hover**-sensitive
targets (`data-maybe-hoverable=true`), and does not measure that annotation
separately (its only ablation removes the *clickable* annotation).

That hover annotation is the one idea in this area the project does not have:
a declared "this element reveals something on hover" signal, distinct from
activation. It is recorded here as an **idea with no evidence behind it** — the
paper supplies no measurement of its value, and this project's own rule (#25,
#44) is that a mechanism is priced on both axes before it ships.

### 3.6 Other things checked that did not pay out

- *Signal-Driven Observation for Long-Horizon Web Agents* (arXiv:2606.06708,
  v1 4 Jun 2026, v2 4 Aug 2026; ICML 2026 workshop). Proposes re-observing only
  when a detector fires on URL transitions, newly visible interactive elements,
  action failures or exogenous browser events. **Position paper — no experiments,
  no benchmarks, no numbers.** Its thesis (observation frequency should decouple
  from action frequency) is already this project's `delta` + scoped-read +
  `browser_batch` design, shipped and measured.
- *Token Efficient Task Execution via Application Behavior Modeling for Web
  Agents* (OdoBot), Ianta & Stroulia, arXiv:2609.13491v1, 11 Sep 2026. 44% fewer
  tokens than Agent-E, 80% fewer than WebVoyager — but on **45 tasks in a single
  application** (Canvas LMS), and the abstract does not describe the mechanism.
  Too narrow and too under-specified to act on.
- Accessibility-tree *repair* literature (arXiv:2608.24913, 2605.27716,
  2606.21926) is about fixing **websites** for human screen-reader users, not
  about an agent reading a page. Not applicable.
- No 2026 declarative affordance standard beyond WebMCP was found.

## 4. Explicitly flagged as UNVERIFIED or discarded

**Discarded — figures attributed to papers that do not contain them:**

- A search summary attributed "**17.3%** of tasks flipping outcome between
  identical-rate runs" to ComponentBench (2608.18307). **That figure is not in
  the paper.** The nearest real number is the 83.1% → 48.9% observation-space
  gap. Do not import it; in particular, do not treat it as a second data point
  beside arXiv:2608.06171's 12–14% rerun noise floor.
- Several 2026 blog posts present WebMCP's `toolname`/`tooldescription`
  declarative attributes as part of the standard. The spec repo says explicitly
  they are not (§1.4).
- Blog adoption statistics for WebMCP (e.g. "41% adoption") and inconsistent
  Chrome version claims (146 vs 149 vs 149–156): **UNVERIFIED**, not used.

**Numbers taken through a page-summarising fetch rather than my own reading of
the table — identifier and direction reliable, last digit may not be:**

- Region4Web's WebArena and WebArena-Lite tables (§1.3). The fetch read only the
  first 100k of 114k characters.
- WebChallenger's benchmark scores (§2.1) — first 100k of 172k characters.
- BreakingWeb's patience table (§1.5) — first 100k of 198k characters; cells
  appear to be n = 25, and the paper itself cautions on per-primitive samples.
- Affora's study numbers (§2.4, §2.5) — single-author preprint, no peer review,
  and I did not verify which eight component libraries were tested.
- arXiv:2604.01535's Table 1 (§1.1) — this is the one I would re-derive before
  acting, because it is the finding that would change the most.

**Could not establish:**

- Whether ComponentBench provides per-step element ground truth. The paper does
  not describe it; absence is not confirmed.
- WebServ's original submission date (only the v2 arXiv stamp, 17 May 2026, was
  visible) and which hover events it wraps.
- Region4Web's region-boundary claim has no ablation behind it — this is
  *established*, not unverified: I looked for the baseline and Tables 2 and 4 do
  not contain one.

## 5. Bibliography

Ordered by relevance to this project.

1. **Read More, Think More: Revisiting Observation Reduction for Web Agents.**
   Enomoto M., Obara R., Zhang H., Oyamada M. arXiv:2604.01535v1, 2 Apr 2026.
   *Measured:* HTML vs accessibility-tree observations on WorkArena L1 (330
   tasks) across 11 models and several thinking budgets; strong models gain up to
   +17.5 points from HTML, weak models lose up to 18.8.

2. **ComponentBench: Diagnosing Component-Level Failures in Computer-Use Agents.**
   Guan T., Lin X., Cheng-Yue R., Wang X., Zhou S. arXiv:2608.18307v1,
   18 Aug 2026. COLM 2026. Code: github.com/TianchenGuan/ComponentBench.
   *Measured:* 2,910 oracle-verified tasks over 97 component types in generated
   Next.js apps, seven models × four observation/action spaces; observation space
   alone moves success >30 points (GPT-5 mini 83.1% AX-tree → 48.9% Pixel).

3. **Region4Web: Rethinking Observation Space Granularity for Web Agents.**
   Kwon D., Lee D. arXiv:2605.07134v1, 8 May 2026.
   *Measured:* WebArena (812 tasks); a learned EdgeClassifier segments the AXTree
   into regions and a persistent PageDigest cuts observation tokens 16–54% while
   raising success 1.7–3.0 points on most actors.

4. **Constructing Challenging Browser-Use Tasks by Controlled Environment
   Interventions.** Yin X., Guan T., Wang J., Cao W., Lin D.X., Cheng-Yue R.,
   Long K., Wong K., Dhingra B., Wang X., Zhou S. arXiv:2609.35814v2,
   20 Oct 2026.
   *Measured:* 519 intervention variants in 29 families over four layers scored
   on final backend state; "patience" (tail latency, progressive delay) drops
   agent pass rates by 0 to 24 points.

5. **WebChallenger: A Reliable and Efficient Generalist Web Agent.**
   Hwang J., Zhang X., Padwal V. arXiv:2606.10423v1, 9 Jun 2026.
   *Measured:* WebArena 56.3 / VisualWebArena 48.7 / Online-Mind2Web 51.0 /
   WorkArena 70.9, using a clickable predicate of tag + event-attribute + ARIA
   role + `cursor:pointer` behind a visibility/`aria-hidden`/`disabled` gate.

6. **Affora: A Design System for Agent-Friendly Interfaces.** Gao J.
   arXiv:2609.19125v1, 16 Sep 2026.
   *Measured:* three controlled studies — plain semantic HTML 91% vs component
   libraries 86.7–68.3%; exposing choices and state lifted a repair sequence
   67% → 90%; DOM-channel completion 99.5% across themes vs 92% pixel.

7. **WebMCP — specification repository and Declarative API Explainer.**
   github.com/webmachinelearning/webmcp (spec first published 2025-08-13; repo
   active 2026); `declarative-api-explainer.md`.
   *States:* only the imperative `document.modelContext.registerTool()` API is
   specified; `toolname` / `tooldescription` / `toolautosubmit` /
   `toolparamdescription` are an explainer-stage proposal with how they surface
   in `getTools()` listed as an open question.

8. **MCP-Driven Accessibility Tree Standardization for AI-Powered Screen Reader
   Agents.** Ramineni V., Saksena N., Agarwal A.K., Bidkar D.M., Pothineni B.,
   Maruthavanan D., Butra L., Chintham S.K. arXiv:2608.24898v1, 13 Jul 2026.
   *Measured:* nothing — conceptual architecture proposing bounded subtree
   requests (`a11y://tree/{session}?root=&depth=`) and update notifications;
   comparison table is qualitative.

9. **WebServ: A Full-Stack and RL-Ready Web Environment for Training Web Agents
   at Scale.** Lu Y., Wang Z., Huang J., Liu H., Gesi J., Han Y., Fu S.,
   Zheng T., Tang X., Luo C., Sang Y., Lai J., Wang D. arXiv:2510.16252v2
   (v2 stamped 17 May 2026).
   *Measured:* an RL-ready environment whose parser detects interactive elements
   by native controls / ARIA roles / `cursor:pointer`, monkey-patching
   `addEventListener` to annotate hover-sensitive targets (annotation not
   separately ablated).

10. **Signal-Driven Observation for Long-Horizon Web Agents.** Gaur S., Lane I.
    arXiv:2606.06708v2 (v1 4 Jun 2026; v2 4 Aug 2026). ICML 2026 workshop.
    *Measured:* nothing — position paper proposing that observation be
    re-triggered by URL change, newly visible interactive elements, action
    failure or exogenous browser events.

11. **CAP: A Scalable Benchmark for Evaluating Cross-Site Browser Agents with
    Complex Actions and Perception.** Xu Z. et al. (16 authors).
    arXiv:2608.08392, 9 Aug 2026. COLM 2026.
    *Measured:* 420 cross-site tasks over 108 real websites / 24 domains under a
    verifiable agent-as-a-judge framework; perception-heavy interaction is the
    reported bottleneck.

12. **Token Efficient Task Execution via Application Behavior Modeling for Web
    Agents.** Ianta A., Stroulia E. arXiv:2609.13491v1, 11 Sep 2026.
    *Measured:* 45 Canvas LMS tasks; 44% fewer tokens than Agent-E and 80% fewer
    than WebVoyager, at higher success than WebVoyager.

13. **MAG: A Web-Agent Benchmark and Harness for Multimodal Action and Guide
    Generation.** arXiv:2607.10079.
    *Measured:* a controlled Set-of-Marks vs raw-pixel-coordinate grounding
    comparison with prompts/observations/scoring fixed; outcome is
    model-dependent (a 9B model: 13.2% SoM vs 9.2% pixel). **(abstract-level,
    unverified table.)**

14. **NEXT-EVAL: Next Evaluation of Traditional and LLM Web Data Record
    Extraction.** arXiv:2505.17125, 2025.
    *Measured:* a benchmark for repeated-record extraction, included here as the
    most recent item in a line of work where 2026 produced no new method.
